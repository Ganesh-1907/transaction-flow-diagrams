Free: no transaction row. Paid: the participant is saved first, then one transaction row per Pay now click, created by the payment webhook. Special case, paid with a zero total: no payment step, but BX writes a CONFIRMED transaction itself.

Built URL

Payment step link PAID: rx builds it after step 2. Any link with ?ref= opens step 3:
<rx origin>/<locale>/programs/<program_id>?ref=<registration_id>

registration_id is the participant's registration UUID, returned by the register call. rx also sends it to CAPS as participant_id when Pay now is clicked.

Thank you link PAID: after the gateway, success, processing or pay later goes to:
<rx origin>/<locale>/programs/<program_id>/thankyou?ref=<registration_id>&caps_transaction_id=<CAPS id>

Thank you link FREE and ZERO FEE: Submit goes straight to the thank-you page. There is no payment, so there is no CAPS id:
<rx origin>/<locale>/programs/<program_id>/thankyou?ref=<registration_id>

Fail link PAID: failed, or any other status, goes to:
<rx origin>/<locale>/programs/<program_id>/failed?ref=<registration_id>&caps_transaction_id=<CAPS id>

Retry link PAID: the Try again button on the failed page opens:
<rx origin>/<locale>/programs/<program_id>/retry-payment?ref=<registration_id>&caps_transaction_id=<CAPS id>

The links never change. If the payment is already finished, opening the step 3 link goes to the thank-you page.

  • FREE: one step. Submit saves the user and the participant in one request. There is no payment, no CAPS order and no payment webhook, so no program_participant_transaction row is created.
  • FREE: the participant is visible straight away and the confirmation email goes out at registration. Free is decided by the event (is_paid_program is false), not by the amount.
  • PAID: Step 1 writes the users row. Step 2 inserts the program_participant row. No transaction row exists yet.
  • PAID: every Pay now click in step 3 creates one more transaction row. The payment webhook inserts it, one row per CAPS order.
  • PAID: T1 abandoned is PENDING, later FAILED by the rescue service. T2 declined is FAILED, the retry email is sent and the Failed page offers Try again. T3 paid is CONFIRMED.
  • PAID: if the bank is still processing, T becomes PROCESSING, the thank-you page says processing and no email is sent yet. A CONFIRMED transaction is never changed back by a later webhook.
  • SPECIAL CASE, zero fee: the event is paid but the payable total is 0 (fee level price 0, or a discount code brings it to 0). Steps 1 and 2 are the same as a paid event, but the Step 2 button reads Submit and there is no step 3.
  • SPECIAL CASE: BX writes the CONFIRMED transaction itself, in the same request that inserts P1. rx makes no CAPS call. T has total_amount 0, no payment method and no payment id.
  • Compare: a free event has no transaction row. A paid event gets its rows later, from a webhook. A zero-fee event gets its row at registration, from BX.

Single-participant registration. Group and ticketed events have their own pages and register calls, with the same free / paid / zero-fee rules (in a group registration only the primary participant gets the zero-fee transaction).
